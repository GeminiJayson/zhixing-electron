# Triage 标签

五个角色，与仓库里的同名标签一一对应。**收 issue 时先打其中一个。**

| 标签 | 含义 | 谁来做 |
| --- | --- | --- |
| `needs-triage` | **还没评估**。新 issue 的默认落点 | 维护者 |
| `needs-info` | **等信息**。描述不足以判断 | 提问者 |
| `ready-for-agent` | **规格完整**，可以交给 AFK agent 做 | Agent |
| `ready-for-human` | **需要人做**（要判断、要凭据、要上手点） | 人 |
| `wontfix` | **决定不做** | — |

## 为什么 `ready-for-agent` 的门槛要严

**"规格完整"指**：目标明确、验收标准可检验、涉及的文件范围能圈出来。
**差一条就会返工** —— agent 会按自己的理解补全缺失的部分，而补错比你写清楚更贵。

## `wontfix` 也要留理由

**打 `wontfix` 时在评论里写清"为什么不做"**，否则半年后有人会重新提一遍。

这个仓库里的例子：**窗口材质（mica / 亚克力）** —— 用截图对比证明过"主界面各层背后是
彼此的同色底，模糊接近恒等变换"（同样参数只变化 0.6%），**要真做出层次只能换
`backgroundMaterial`，代价是窗口变直角**。**这是产品决策，不是没做。**

## 别把"不做"和"没做"混在一起

**清单里两者混着放，会让"完成度"永远上不去。** 这个仓库在 `README.md` §15 单独列了
"已决策不做"，`docs/01` 里也用「有意简化」区分于「未实现」。
