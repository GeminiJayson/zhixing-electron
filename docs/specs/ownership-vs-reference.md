# 概念定义：「归属」与「引用」的边界

> 状态：**待审核** · 提出人：用户 · 审视：AI · 关联 #2 #3

## 一、结论：用户的定义是对的

| 概念 | 含义 | 数据来源 |
| --- | --- | --- |
| **归属** | **容器关系** —— 它属于哪个文件夹 / 列表 / 分类 | `note.folder_id`、`task.list_id` |
| **反向链接** | **谁引用了我**（笔记与任务都算） | `note_link` 反查、`task.notes_md` 里的 `[[我]]`、`task_note_context` |
| **正向引用** | **我引用了谁** | `note_link` 正查 |
| **属性** | 这条内容的元数据 | `note.props` |

**判别标准一句话**：归属是「我装在哪个盒子里」，引用是「谁在正文里提到我」。
前者是唯一的一对多容器关系，后者可以是多对多的、出现在正文里的。

## 二、证据：代码里早就有正确答案

图谱模块的分类规则（`src/main/db/graph.ts:27-30`）：

```
 * - 任一端是 anchor（段落锚）→ 引用虚线；
 * - 两端都在 {note, dangling} 内（但不含 dangling↔dangling）→ 引用虚线；
 * - 其余 → 归属实线。
 * 注意 folder→note 是**归属实线**（容器→内容），不是引用。
```

**图谱早就把「文件夹→笔记」划为归属、「引用」划为引用。** 走偏的只有界面文案与分组。

任务对笔记的关联本质是引用 —— `src/main/db/note-assoc.ts:5`：

> 任务备注（task.notes_md）里写着 `[[旧标题]]` —— 笔记改名后这句就悬空了。

## 四、修复方案

### 第 1 步：信息区重新归类（结构）

| 栏 | 现有内容 | 改为 |
| --- | --- | --- |
| **属性** | 不变 | 不变 |
| **反向链接** | 只有笔记反链 | **笔记反链 + 引用了这篇的任务** |
| **正向引用** | 不变 | 不变 |
| **归属** | 文件夹 + **任务关联** | **只有文件夹/分类** |

数据层**不用改**：`noteAttachedTasks(noteId)` 返回的本来就是「引用了这篇的任务」，
只是此前被摆错了栏。

### 第 2 步：动作拆开（交互）

- 「归属」栏底部：只留「**移动到文件夹…**」
- 「反向链接」栏底部：新增「**关联到任务…**」（把引用了这篇的任务挂上来）

### 第 3 步：文案对齐（文案）

| 旧 | 新 |
| --- | --- |
| 本笔记归属的任务 | 引用了这篇的任务 |
| 归属到任务 | 关联到任务 |
| 把本笔记归属到某任务或某文件夹 | 拆成两个按钮，各自说各自的事 |
| 归属 chip 文案：文件夹名 / 关联 N 个任务 | **只显示归属**（文件夹名）—— 引用数与信息区的反向链接栏一致，不塞进 chip |

### 第 4 步：全局自查（已做，结论：无需改动）

| 位置 | 现状 | 结论 |
| --- | --- | --- |
| 图谱边分类 | folder→note 归属实线、note→note 引用虚线 | ✅ **已正确** |
| 任务页「关联笔记」 | 用 task_note_context 段落锚 | ✅ 正确 |
| 工作流「SOP 文档」 | 是绑定，不涉及归属 | ✅ 正确 |
| 任务页「收件箱（未归属）」 | 归属 = 未归入任何列表 | ✅ **正确，且与本次定义一致** |

**所以改动面只有 NotesPage 一处**，不动数据层、不动图谱、不动任务页。

## 五、一个需要你拍板的点

**「关联到任务」这个动作，是否应该自动写进任务备注？**

现在 `attachTaskNote` 建的是 `task_note_link`（一条关系记录），
而任务引用笔记的**另一种**形式是任务备注里的 `[[标题]]`（`note-assoc.ts` 处理的就是它）。

两条路并存：
- **A. 保持现状** —— 关联是一条记录，不出现在任务备注里
- **B. 关联时同时往任务备注追加 `[[标题]]`** —— 关系在任务正文里可见，改名时也会被 repair 逻辑照顾到

我倾向 **A**：备注是用户写的内容，工具往里塞东西要谨慎。
但如果你希望「任务里能一眼看到关联了哪篇笔记」，那就选 B。
