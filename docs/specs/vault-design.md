# 密码保险箱（Vault）设计方案

> 状态：**待审计** · 目标版本：v1.20.0 · 关联：[#待建]

本文只描述方案，不含实现。请重点审计 §2 威胁模型、§6 与现有功能的边界、§10 遗漏项。

---

## 1. 目标与非目标

### 做

- 存账号密码、网址、备注，**落库即为密文**
- 一个主密码解锁；解锁前看不到任何条目的内容（包括标题）
- 条目可搜索、可复制、可增删改
- 与现有应用的观感一致（同样的玻璃层、控件、主题包）

### 不做

- 浏览器插件 / 自动填充（离本项目形态太远）
- 多设备同步、共享（本项目是本地优先、单机单库）
- 附件（先把文本类做完）
- 密码生成器（**建议单列一个小需求**，见 §10.3）

## 2. 威胁模型

这一节决定了后面所有取舍，请优先审。

### 防得住

| 场景 | 为什么防得住 |
| --- | --- |
| 数据库文件被拷走（U 盘、网盘同步、整机备份） | 内容是密文，没有主密码解不开 |
| 电脑被他人短暂使用、随手打开这个应用 | 未解锁时看不到任何内容 |
| 数据库被误提交到 Git / 发给别人 | 同上 |
| 备份文件泄漏 | 备份是整库拷贝，同样是密文 |

### 防不住（**必须让用户知道**）

| 场景 | 说明 |
| --- | --- |
| 已解锁状态下的内存转储 | 主密钥在进程内存里，这是所有本地密码库的共同限制 |
| 键盘记录器 / 屏幕录制 | 在操作系统层面，应用无能为力 |
| 有管理员权限的实时攻击者 | 可以直接读进程内存 |
| 应用自身的逆向 | Electron 应用的前端代码是可读的 |

**结论**：这个功能防的是"**文件被拿走**"，不是"**电脑被控制**"。方案与文案都要与此一致，不做超出能力的承诺。

## 3. 密码学设计

全部用 `node:crypto`，不引入第三方密码学库。

### 3.1 密钥派生

```
主密码 --scrypt--> 主密钥（32 字节，只在内存）
```

- **算法**：`scrypt`（Node 内置；本项目不引 argon2，避免原生依赖）
- **参数**：`N = 2^17, r = 8, p = 1, keylen = 32`
- **盐**：16 字节随机，每库一个，存在 `vault_meta`
- **参数一并入库**（`kdf_params` JSON），便于以后提高强度而不破坏旧库

**关于强度与耗时的取舍**：`N = 2^17` 约需 128 MB 内存、单次约 0.3–1 秒。
**这个延迟是特性不是缺陷** —— 暴力破解的成本主要来自它。
但要让 UI 明确显示"正在解锁"，否则用户会以为卡死。

### 3.2 加密

- **算法**：AES-256-GCM
- **IV**：每条目**每字段**独立 12 字节随机（GCM 下 IV 复用是致命的，必须逐字段生成）
- **AAD**：绑定 `entry_id + 字段名`
  - 作用：防止把 A 条目的密码字段挪到 B 条目而不被发现
- **认证标签**：GCM 自带（16 字节，附在密文尾部）

### 3.3 主密码校验

不存主密码的任何哈希，而是：

```
verifier = AES-GCM(主密钥, iv, 固定明文 "zhixing-vault-v1")
```

解锁时尝试解密 `verifier`，解得出即密码正确。
**好处**：校验与加密用同一份材料，不存在"哈希被单独攻破"的路径。

## 4. 存储设计

### 4.1 新表（SCHEMA_VERSION 14 → 15）

```sql
CREATE TABLE IF NOT EXISTS vault_meta (
  id            INTEGER PRIMARY KEY CHECK (id = 1),  -- 单行表
  kdf_salt      BLOB    NOT NULL,
  kdf_params    TEXT    NOT NULL,   -- {"N":131072,"r":8,"p":1,"keylen":32}
  verifier_ct   BLOB    NOT NULL,
  verifier_iv   BLOB    NOT NULL,
  created_at    TEXT    NOT NULL
);

CREATE TABLE IF NOT EXISTS vault_entry (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  title_ct      BLOB NOT NULL,  title_iv      BLOB NOT NULL,
  username_ct   BLOB,           username_iv   BLOB,
  password_ct   BLOB NOT NULL,  password_iv   BLOB NOT NULL,
  url_ct        BLOB,           url_iv        BLOB,
  notes_ct      BLOB,           notes_iv      BLOB,
  tags_ct       BLOB,           tags_iv       BLOB,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_vault_entry_updated ON vault_entry(updated_at DESC);
```

### 4.2 几个刻意的取舍

**① 标题也加密**

标题是"你有哪些账号"的直接泄漏（"招商银行""公司 VPN"）。
代价是列表要**全部解密后才能排序/显示** —— 条目量级是几十到几百，一次解锁后解密全表在内存里做，可接受。

**② 绝不进 FTS**

现有三张 FTS 表（`task_fts` / `note_fts` / `flash_fts`）都是**明文索引**。
保险箱**不建 FTS 表**，搜索在**解密后的内存数组**上做。
这是硬约束：一旦进了 FTS，明文就会落到索引表里。

**③ 不做版本历史**

`note_revision` 那种机制会留下历史密文副本。密文本无害，但会让"删除"变得不彻底，且没有实际价值。

**④ 不做回收站**

删除即真删（同样是为了"删除"语义干净）。

## 5. 解锁、锁定与生命周期

### 5.1 状态机

```
未初始化 --设置主密码--> 已锁定 --输入正确主密码--> 已解锁
                              ^                        |
                              +---- 自动锁定 / 手动锁定 / 退出 ----+
```

**主密钥只存在于主进程内存**，渲染层拿不到它 —— 渲染层通过 IPC 请求"解密这条"，主进程返回明文。
这样即便渲染层被注入（本应用不加载远程内容，风险很低），也拿不到主密钥。

### 5.2 解锁后的明文缓存

解锁后主进程把**解密结果缓存在内存**（列表要排序、搜索要用）。
这是必要的取舍：每次都全表解密会让列表滚动卡顿。
缓存生命周期严格等于"解锁会话"，锁定即清空。

### 5.3 自动锁定

| 条件 | 默认 | 可调 |
| --- | --- | --- |
| 无操作 N 分钟 | 5 分钟 | 1 / 5 / 15 / 30 / 从不 |
| 应用退出 | 立即 | 否 |
| 手动点「锁定」 | 立即 | — |

"从不自动锁定"是允许的（有些用户就是开着用一天），但要在设置里用警示色标出来。

### 5.4 剪贴板

复制密码后 **30 秒**清除剪贴板 —— 且**只在剪贴板内容仍等于复制出去的值时才清**，
否则会把用户后来复制的东西误删。这是密码管理器的通行做法（KeePass / Bitwarden 都是这个逻辑）。

## 6. 与现有功能的边界（**请重点审计**）

保险箱不是孤岛，现有这几处机制会碰到它：

| 现有机制 | 位置 | 处理方式 |
| --- | --- | --- |
| **全文搜索** | `src/main/db/fts.ts` + 三张 `*_fts` | **完全隔离**：不建索引、不出现在搜索结果里 |
| **数据导出 JSON** | `src/main/db/export.ts` 的 `EXPORT_TABLES` | **默认排除**，详见 §6.1 |
| **任务导出 CSV** | 同上的 `buildTasksCsv` | 不涉及（保险箱不是任务） |
| **笔记导出 ZIP** | 同上的 `buildZip` | 不涉及 |
| **自动备份** | `src/main/db/backup.ts` 的 `autoBackup`（保留 10 份） | **整库拷贝，密文原样进备份 —— 安全**，无需改动 |
| **备份恢复** | 同上的 `restoreBackup` | 恢复后需重新解锁（主密钥不在库里） |
| **回收站** | `src/main/db/trash.ts` | **不接入**：保险箱条目删除即真删 |
| **导入数据** | `importData` | 若导入的库里含 `vault_*` 且主密码不同 → 明确报错，不静默失败 |

### 6.1 导出怎么处理（**需要你拍板**）

| 方案 | 说明 | 风险 |
| --- | --- | --- |
| **A. 默认排除，可勾选包含** | 导出对话框加复选框，默认不勾 | 勾了导出的仍是**密文**，还需原主密码 —— 安全，但用户可能以为"导出了就能用" |
| **B. 永远排除** | 最简单也最安全 | 换机时导不过去，只能用整库备份 |
| **C. 导出时解密成明文** | —— | **不做**：会让"导出"变成绕过主密码的路径 |

**建议 A**，并在勾选后明确提示"导出的仍是密文"。C 无论如何都不做。

## 7. 界面

### 7.1 导航

侧栏新增一项 `vault`，放在 `review` 与 `settings` 之间（第 7 位，`zone: top`），图标用锁形。
需要动三处：`nav.ts` 加 `PageKey`、`App.tsx` 加路由、`i18n` 加文案 —— 这是本项目加页面的固定成本。

### 7.2 三种形态

**① 未初始化**：居中卡片，设置主密码（输两次 + 强度提示 + "忘记无法找回"的确认勾选）。

**② 已锁定**：居中卡片，一个密码框 + 解锁按钮。解锁中显示进度（scrypt 要 0.3–1 秒）。
**失败提示要克制**：统一说"主密码不正确"，不区分"格式错误"与"密码错误"。

**③ 已解锁**：左列表（搜索 + 条目）+ 右详情（编辑表单）。
复用现有的 `.u-card` / `.set-row` / `--control-h` 那套，不新造控件。

### 7.3 列表数据

标题是密文，列表来自主进程解密后的缓存。
**注意**：锁定状态下切回这个页面，不能残留上一次的列表数据（React 状态要跟着清）。

## 8. 主密码不可恢复（**最重要的一条**）

**没有找回密码的机制，这是设计而不是缺陷。**

任何"找回"方案（密保问题、恢复码、邮箱验证）都等于在主密码之外开一条旁路；
而对一个本地优先、无账号体系的应用来说，那条旁路只能存在本地 —— 也就等于把钥匙和锁放在一起。

所以：

- 首次设置主密码时**必须**让用户显式确认"我知道忘记就找不回来了"（勾选框，不默认勾上）
- 设置页提供"**清空保险箱并重设主密码**"（需输入当前主密码 + 二次确认）
- 忘了主密码的唯一出路是清空重建，那部分数据永远取不回来

## 9. 迁移与测试

### 9.1 迁移

- `SCHEMA_VERSION`: **14 → 15**
- `migrate.ts` 迁移链补 15 号步骤（建两张表 + 索引）
- `schema.ts` 的 `SCHEMA_SQL` 同步（新库直接建好）
- 旧库升级不需要用户做任何事；升级后保险箱处于"未初始化"状态

### 9.2 单元测试

| 用例 | 断言 |
| --- | --- |
| 加解密往返 | 明文 → 密文 → 明文 一致 |
| 错误主密码 | 解 `verifier` 失败，且不抛未捕获异常 |
| AAD 绑定 | 把条目 A 的密文放到条目 B 的 id 下 → 解密失败 |
| IV 唯一 | 同一明文加密两次 → 密文不同 |
| KDF 参数持久化 | 换参数后旧库仍能解锁 |
| 锁定清缓存 | 锁定后读列表 → 报"未解锁"而不是返回旧数据 |
| 不进 FTS | 建条目后搜全文 → 搜不到 |

### 9.3 手工验证

- 锁定 → 重启应用 → 仍是锁定态
- 复制密码 → 30 秒后剪贴板被清（改过则不清）
- 自动锁定到点后切回页面，要求重新输入
- **用十六进制查看器打开 `zhixing.db`，搜不到任何明文条目**（最关键，建议做成改动后的固定检查）

## 10. 需要你拍板的点

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | **导出是否包含保险箱**（§6.1） | **A：默认排除、可勾选、勾了也是密文** |
| 2 | **是否要"记住解锁"（`safeStorage`）** | **不做** —— 等于把主密钥从"你的脑子"挪到"当前 Windows 账户"，与 §2 的威胁模型冲突 |
| 3 | 自动锁定默认值 | 5 分钟；下拉 1 / 5 / 15 / 30 / 从不 |
| 4 | 导航位置 | 第 7 位（review 之后、settings 之前） |
| 5 | 主密码最低长度 | 8 位，只提示强度、不做硬性复杂度要求 |
| 6 | **要不要顺带做密码生成器** | 建议**同批做** —— 代码量很小，但显著提升"用户真的会用强密码"的概率 |
| 7 | 条目标题是否加密（§4.2 ①） | **加密**，代价是列表要全解密 |
| 8 | 要不要密码强度提示 | 本地计算，不联网 |

## 11. 工作量估计

| 部分 | 量级 |
| --- | --- |
| 密码学模块（派生 / 加解密 / verifier）+ 测试 | 约 150 行 + 100 行测试 |
| 数据层（两张表 + 迁移 + CRUD） | 约 200 行 |
| IPC 通道（解锁 / 锁定 / 列表 / 增删改 / 复制） | 约 120 行 |
| 渲染层（三种形态 + 列表 + 表单） | 约 400 行 |
| 设置项（自动锁定 / 清空重建） | 约 80 行 |
| i18n / 导航 / 样式 | 约 150 行 |

**合计约 1100 行**，按本项目以往的节奏是 2–3 轮的工作量。

## 12. 分期建议

**第一期（可独立发布）**：设置主密码 / 解锁 / 锁定 / 列表 / 增删改查 / 复制 / 剪贴板清除。

**第二期**：搜索、标签、密码生成器、强度提示、清空重建、导出联动。

建议**先只做第一期**并让你实际用几天 —— 密码库这种东西，用起来才知道哪里别扭。
