## 2. 领域模型：两层，别混在一起

你的描述里最关键的一句是「**原文始终保留**，确保日后查到结论时能找到出处」。
这句话决定模型必须是两层 —— 而现有的 flash + note 正好就是这个形状：

```
原始资料（source）
  文章正文、链接、抓取时间、来源    <- 永不修改，只增不改
  这一层负责"我读过什么"
        |
        |  提炼（人工判断，不是自动摘要）
        v
知识条目（knowledge）
  概念 / 摘要 / 综合分析 / 方法论   <- 会反复修改、会被推翻
  带**可信状态**、带**来源引用**
  这一层负责"我确认了什么"
```

**为什么必须分开**：如果原文和结论混在一张表里，你永远分不清"这是作者说的"还是"我认可的"。
而这两者的可信度完全不同 —— 这正是你提「待确认」的动机。

| | 原始资料 | 知识条目 |
| --- | --- | --- |
| 内容 | 原文（或摘录）+ 出处 | 你自己的表述 |
| 可变性 | **不可变**（只追加） | 可反复修改 |
| 状态 | 未处理 / 已归档 | **待确认 / 可用** |
| 删除 | 几乎不删（那是你的阅读史） | 可以删（结论被推翻了） |

## 3. 六个区域怎么落

你列的六个区域**性质并不相同** —— 前三个是工作区，后三个是知识区：

| 区域 | 性质 | 落法 |
| --- | --- | --- |
| **收件箱** | 工作区 | 复用 flash（已有出处字段与状态） |
| **笔记** | 工作区 | note + kind = note（读完的理解、疑问） |
| **项目记录** | 工作区 | note + kind = project（过程与结果） |
| **知识区域** | 知识区 | note + kind 属于 概念/摘要/综合分析/方法论 |
| **输出** | 知识区 | note + kind = output |
| **归档** | 知识区 | note 的 archived_at 非空（**状态**，不是目录） |
| **踩坑库** | 知识区 | note + kind = pitfall（有专属模板，见 §6） |

**为什么"归档"做成状态而不是目录**：归档是"我现在不看它了"，是个**可逆的状态**。
做成目录的话，每次归档都要移动文件，而且移进去之后就分不清它原本属于哪一类了。

## 4. 资料入库流程

你描述的流程是「交给工具 -> 查重 -> 标记待确认 -> 核对 -> 放进可用区域」。落成四步：

### 第 1 步：入箱

输入：正文 / 链接 / 标签（可选：标题、作者、抓取时间）

- **查重**：URL 精确匹配 + 正文前 200 字做指纹（现有 block-fingerprint.ts 已有纯 JS SHA-1，可直接用）
- **重复时不覆盖**，而是提示"这条已经在收件箱里（2026-09-30 收）"，让你决定
- **原文原样存下，不做任何摘要** —— 摘要是下一步的事

### 第 2 步：标记待确认

**所有新收资料都进"未处理"**；从收件箱提炼出的知识条目**一律是「待确认」**。
这条是硬规则：不存在"直接创建一条可用知识"的入口。

### 第 3 步：核对（这里是人做的事）

你列的核对项，落成**结构化的检查清单**（勾选状态存在知识条目上）：

| 检查项 | 记什么 |
| --- | --- |
| 关键说法有依据 | 是 / 否 / 部分；选"否"时要求填理由 |
| 方法适用场景明确 | 适用条件、不适用条件 |
| 与其他资料一致 | 冲突的话链接到冲突的那条（见 §7） |
| 时效性 | 结论的有效期 / 是否有更新版本 |

**为什么结构化而不是一个"已核对"复选框**：三个月后你看到一条结论，
真正想知道的是「**当初凭什么信它**」，而不是「我打过勾」。

### 第 4 步：放进可用区域

核对通过 -> 状态从「待确认」变「可用」-> 出现在知识区默认视图里。
**待确认的条目不会消失**，只是不在默认视图，可随时切到"待确认"筛选继续处理。

## 5. 「待确认」状态机（本方案的核心）

```
  draft（待确认） --核对通过--> verified（可用）
        ^                            |
        +-------- 发现问题，退回 -----+
                                     |
                                 archived（归档）
```

**两个刻意的决定**：

**① 允许从「可用」退回「待确认」**
知识会被推翻。发现某条结论已不成立时，正确动作是退回待确认并记下原因 ——
而不是直接删掉。删掉的话，你下次还会踩同一个坑。

**② 待确认条目在全局搜索里也带标记**
搜索命中一条待确认知识时，结果显示上要有一眼可见的标记。否则你写东西时引用了它，
却不知道它其实还没核对过 —— 那这个状态就白设了。

## 6. 七个知识类型各自的模板

你列的类型里，有三类值得给**固定结构**，因为它们填起来容易漏项：

**概念（concept）** —— 你说"记录一个词的具体含义及来源"：

```
定义（我自己的话）
它不是什么（边界，防止望文生义）
来源（必填，指向原始资料）
相关概念（双向链接）
```

**方法论（method）** —— 你说"能拿来做事的方法，包括具体步骤和适用场景"：

```
什么时候用它（场景）
什么时候别用（反场景，最容易漏的一项）
步骤（有序列表）
前置条件 / 需要的东西
失败的样子（做错了会怎样）
```

**踩坑库（pitfall）** —— 你说"问题出现过程及下次注意事项"：

```
现象（当时看到什么）
排查过程（试过什么、排除掉什么）
根因（真正的那个）
修复（怎么好的）
下次怎么避免（可执行的，不是"要小心"）
```

**踩坑库的价值全在"排查过程"** —— 现象和结论网上都有，只有排查路径是你自己的。
所以模板里它排在根因前面，强制你先写它。

> 另外四类（摘要 / 综合分析 / 输出 / 归档）用自由格式即可，它们本来就没什么固定结构。

## 7. 综合分析：多个来源的对照

你写的是"记录多份资料是否相互印证或矛盾"。这需要一条**专门的引用关系**，
不能只靠双向链接 —— 链接表达"相关"，而这里要表达的是"**支持 / 反对**"：

```
综合分析条目
  |- 支持 -> 资料 A（+ 支持的是哪一点）
  |- 支持 -> 资料 B
  +- 反对 -> 资料 C（+ 反对的是哪一点、如何解释这个矛盾）
```

**「如何解释这个矛盾」是必填的**：
一条既列出支持又列出反对、却不解释为什么还是倾向某一边的综合分析，等于没做。

## 8. 可追溯性（你说的"原文始终保留"）

这是整个方案里**最值得做扎实**的一条。四条规则：

1. **知识条目的来源是必填项** —— 没有来源的知识条目只能存为「待确认」
2. **一个来源可以长出多条知识**（一篇文章可以提炼出 3 个概念 + 1 个方法论）
3. **删除来源时**：若它仍被知识条目引用，**不允许直接删**，要提示"有 4 条知识引用了它"
4. **知识条目上永远显示"来源：XXX"**，点一下就跳到原文

现有 note_link 表可以承载，但要加一个 **link_kind**（derived_from / supports / contradicts）
来区分"相关"与"来源"。

## 9. 需要你拍板的点

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | **七个类型做成枚举还是自由目录** | **枚举**（固定 7 类 + 各自模板）；目录能表达"在哪"，不能表达"是什么"，而模板要靠类型驱动 |
| 2 | **原文存全文还是摘要 + 链接** | **全文**。链接会失效，这是"日后能找到出处"最大的风险；全文占不了多少空间 |
| 3 | **入库是否需要抓取网页** | **第一期不做**。先支持粘贴正文 + 链接；抓取涉及反爬、编码、正文提取，是另一个工程 |
| 4 | **「待确认」是否影响搜索排序** | **影响**：待确认条目排在可用条目之后，且带可见标记 |
| 5 | **核对清单是必填还是提示** | **提示，不强制**。但"关键说法有依据"若选"否"，**不允许**转为可用 |
| 6 | 笔记 / 项目记录要不要也用固定模板 | **不要**。它们本来就该自由 |
| 7 | 归档是否自动 | **手动**。自动归档（如 90 天没动）会把你还想留着的东西藏起来 |
| 8 | 是否需要"知识成熟度"仪表盘 | **第一期不做**，先用一段时间看你会不会去看 |

## 10. 与现有功能的边界

按上一轮保险箱那次的教训，先把会碰到的地方列清楚：

| 现有机制 | 处理 |
| --- | --- |
| **全文搜索 FTS** | 原文与知识条目都进索引（都是你自己写的东西，不涉及加密）；**但搜索结果要带类型与可信状态** |
| **图谱** | 知识条目按 kind 分色；derived_from 引用用实线，普通链接用虚线 |
| **导出** | 新增字段一并导出；来源引用导出为可读的 URL 而不是 id |
| **回收站** | 知识条目删除进回收站（现有 trash.ts），原文不进（它不可变） |
| **版本历史** | 知识条目沿用 note_revision；**原文不要版本历史**（它不该被改） |
| **快速捕获窗** | 直接进"收件箱"，与新的原始资料是同一层 |
| **密码保险箱** | 完全隔离，两者不共享任何表（上一轮已确认） |

## 13. 我想提醒的一件事

这套流程的价值全在「**核对**」那一步，而它**恰恰是最容易被跳过的一步**。

所以方案里做了两个刻意的摩擦：

1. **不存在"直接创建可用知识"的入口** —— 想标为可用，就得走核对
2. **待确认的标记会出现在搜索结果里** —— 你没法假装没看见

如果这两条也去掉了，那这就只是又一个"笔记分类"功能，
而分类是解决不了「我当初凭什么信它」这个问题的。
