# 第三期两项的调研与方案

本文只描述调研结论与方案，不含实现。

## 一、网页正文抓取

### 1.1 调研发现

**项目已有网络能力**：`src/main/ai.ts:188` 与 `src/main/task-sync.ts:291` 已经在用 `fetch`，
所以这件事**不需要引入任何新依赖**。

**同类产品怎么做**：思源笔记的浏览器插件（`siyuan-note/siyuan-chrome`）把内容提取放在
**扩展侧**，而不是桌面端。这个选择很关键，它决定了整个方案的形状 —— 见下。

### 1.2 核心决策：抓取应该由浏览器扩展做，不是主进程

这是本方案最重要的一条判断。两条路的差别不是"方便不方便"，而是**能不能用**：

| | 主进程 fetch | 浏览器扩展提取 |
| --- | --- | --- |
| 拿到的东西 | **原始 HTML** | **渲染后的 DOM** |
| SPA / 前端渲染站点 | ❌ 拿到空壳 | ✅ 正常 |
| 需要登录的页面 | ❌ 没有 cookie | ✅ **带着用户自己的登录态** |
| 付费墙 / 内网文档 | ❌ | ✅ 用户在页面里就说明他有权限 |
| 反爬（UA 检测、JS 挑战） | ❌ 容易被挡 | ✅ 就是浏览器本身 |
| 编码识别 | 要自己猜 | 浏览器已处理好 |

**结论**：主进程 fetch 做这件事，只能覆盖"静态的、公开的、无反爬的"页面 ——
而这类页面恰恰是**最不需要存档的**（随时还能再打开）。真正想存下来的往往是
需要登录才能看的内容，那只有扩展能做。

**而且我们已经有扩展了**（`browser-extension/`），加一条提取路径的边际成本很低。

### 1.3 方案

**主路径：扩展提取**

```
用户在页面上点扩展图标（或快捷键）
  -> content script 调 Readability 提取正文
  -> POST 到 /vault/... 同款的本地端点（新开 /capture 分支）
  -> 主进程按"原始资料"入库：正文 + URL + 标题 + 抓取时间
```

- 提取算法用 **Mozilla Readability**（把 `@mozilla/readability` 打包进扩展，约 +100KB）——
  自己写正文提取是不现实的，那是个需要持续维护的启发式算法
- 提取失败（Readability 返回空）时**回退到 `document.body.innerText`**，
  并明确告诉用户"这条是全文抓的，可能含导航和广告"
- **不做自动抓取** —— 只有用户显式点一下才抓。自动抓取会把浏览历史变成知识库，
  那不是这个功能的目的

**降级路径：主进程 fetch**（可选，第二刀）

用户直接粘贴一个 URL 到收件箱时，主进程可以试着 fetch 一次。
**但要如实标注**："这是原始 HTML 提取的，可能不完整"。
我倾向**第一版不做这条路** —— 它带来的失败体验（拿到空壳、被反爬挡住）
比它带来的便利更显眼。

### 1.4 与现有能力的衔接

- **收件箱**：抓下来的东西直接进 `flash`（原始资料那一层），不是知识条目 ——
  它还没经过提炼，本来就不该是知识
- **查重**：用 URL 精确匹配 + 正文指纹（`block-fingerprint.ts` 已有纯 JS SHA-1）
- **保险箱**：完全不相关，两条路不共享任何东西

### 1.5 明确不做的

- **不做正文提取的质量承诺**：不同站点的成功率会有明显差别，这是所有同类工具的共同现状
- **不做批量抓取 / 爬虫**：这个功能是"存下我正在看的这一篇"，不是"下载一个站点"
- **不做图片下载**：第一版只存文字。图片会让"原始资料"变成一个存储管理问题

## 二、知识成熟度视图

### 2.1 先说一个反对意见

方案 §9 第 8 条我当时写的是"第一期不做，先用一段时间看你会不会去看"。
现在我的看法更具体了：**"成熟度"这个词本身就是模糊的**，
如果不先定义"成熟"指什么，做出来的就是一个好看但没人看的仪表盘。

所以这一节的重点不是"怎么做图"，而是**"到底该看哪几个数"**。

### 2.2 数据层现在能算出什么

我把现有字段能支撑的指标全列出来，并标上我的判断：

| 指标 | 怎么算 | 有没有用 |
| --- | --- | --- |
| **待确认积压量** | `verified_at IS NULL` 的条数 | ✅ **最有用** —— 它是"你收了但没处理"的直接度量 |
| **孤立知识** | 有来源但 `derivedFrom` 为空的知识条目 | ✅ **很有用** —— 提炼了却没人用，说明它可能是自娱自乐 |
| **无来源的知识** | `kind` 属知识类但 `incomingSources` 为空 | ✅ 有用 —— 它们永远卡在待确认 |
| **被引用排行** | 按 `derivedFrom` 计数排序 | ⚠️ 有用但**不适合放仪表盘**：它是"哪些值得再看一眼"，属于列表不属于指标 |
| **各类型分布** | `GROUP BY kind` | ⚠️ 好看，但**不驱动任何行动** |
| **核对通过率** | 可用 / 总数 | ⚠️ 这个数**越接近 1 越没意义**（说明你从不退回） |
| **陈旧度** | `freshness` 字段填了才有 | ⚠️ 依赖用户填写，填的人少就没数据 |
| **增长曲线** | 按 `created_at` 分组 | ❌ 好看但没用 |

**我的判断**：真正有用的只有**前三个**，而且它们都是"**待办**"性质的数字 ——
它们回答问题"我现在该去处理什么"，而不是"我做得怎么样"。

### 2.3 方案：不做仪表盘，做三个数字

```
笔记页筛选条右侧：
  待确认 12 · 无来源 3 · 未被引用 27
```

每个数字**可点**，点下去就是对应的筛选。

**为什么不做成独立页面 / 图表**：

1. **这三个数的价值在于"提醒你去处理"，不在于"回顾"** —— 提醒要出现在你本来就待着的地方，
   而不是一个要专门点进去的页面
2. **图表需要数据量**：30 条笔记画分布图，得到的是一堆没有统计意义的柱子
3. **先验证会不会用**：如果这三个数你从来不看，那仪表盘更不会看

### 2.4 如果后面确实需要仪表盘

那时候再基于**实际使用数据**决定画什么 —— 比如你可能会发现
"待确认积压"一直在涨，那值得一张按周的趋势图；
而"类型分布"如果三个月没变过，就不该占地方。

| 1 | **抓取走扩展还是主进程** | **扩展为主**（能处理登录态与 SPA）；主进程 fetch 第一版不做 |
