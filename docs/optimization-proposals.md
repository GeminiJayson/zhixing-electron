# Electron 版优化建议（待批准）

> 本文档只记录**改进想法**。
> 本文档中的项目**未经批准不实施**。
> 批准方式：逐条回复编号即可。

## 背景

记录的触发点是实现过程中暴露出来的结构性问题——它们不是功能缺失，
而是当前实现的**工程取舍留下的债**，改动会影响面较大，所以单列出来等你决定。

---

## O1 · settings 表缺少类型层（本次 121.5px 事故的根因） ✅ 已完成

**现状**：`settings` 表所有值都是字符串，读取处各自 `Number()` 转换。启动时应用设置的
代码漏了一次转换，`"12" + 1.5` 拼成 `"121.5"`，导致整屏字体被放大到铺满界面。

**建议**：加一个 `shared/settings.ts`，集中声明每个键的类型与默认值，读写都走它：

```ts
const SCHEMA = { font_size: num(12), task_row_height: num(30), theme_mode: str('light'), ... }
settings.font_size   // number，不可能拿到 string
```

**代价**：约 80 行，改 3 处调用点。**收益**：这类拼接错误在类型层直接不可能发生。
**风险**：低。**建议优先级**：高。

---

## O2 · 数据层单文件过大 ✅ 已完成

**现状**：`src/main/db.ts` 已约 1500 行，涵盖任务/笔记/图谱/工作流/回顾/设置/收件箱七块。
**建议**：按域拆成 `main/db/{tasks,notes,graph,workflow,review,settings,inbox}.ts`，
`db.ts` 只保留连接管理与 `registerDbHandlers` 汇总。

**代价**：纯搬迁，约 1 小时，无逻辑改动。**收益**：可读性与并行修改能力。
**风险**：低（纯移动）。**建议优先级**：中。

---

## O3 · 每次操作整页重查，缺增量刷新 ✅ 已完成

**现状**：本实现是「操作完 → 重新查一遍 → setState」。当前数据量（14 任务 / 12 笔记）无感，
但若任务上千、图谱上百节点，会明显卡顿。

**建议**：引入轻量事件层（`shared/events.ts`，几十行的订阅表），
数据写入方 emit，页面按需订阅；先只接图谱与反链两处最重的。

**代价**：中等。**收益**：大列表/大图下的响应性。**风险**：中（状态同步可能引入新 bug）。
**建议优先级**：中（等真的有性能问题再做，现在属于过早优化）。

---

## O4 · 长列表缺虚拟滚动 ✅ 已完成

**现状**：任务树、笔记树、闪念列表都是全量渲染 DOM。
**建议**：超过 300 行时启用窗口化渲染。
**代价**：中等（需引入或自写虚拟列表）。**建议优先级**：低（先量到实际卡顿再说）。

---

## O5 · 图谱布局未复用位置 ✅ 已完成

**现状**：`GraphPage` 每次加载都重建力模拟，节点会重新跑一遍布局，
同一份数据来回切换视图时位置会变。
**建议**：按 `composite_identity` 缓存坐标，重进时先套用旧坐标再微调。
**收益**：观感稳定。**风险**：低。**建议优先级**：中。

---

## O6 · 打包与分发未配置 ✅ 已完成

**现状**：只有 `npm run build`（构建 `out/`），没有 `electron-builder` 配置，
不能出 `.dmg` / `.exe`；应用图标、签名、公证、自动更新都未做。
**建议**：加 electron-builder + 应用图标（macOS 需要 `.icns`）。
**代价**：半天（含签名）。**建议优先级**：高（若要给非开发者用）。

---

## O7 · 链路检查是脚本式的，未接测试框架 ✅ 已完成

**现状**：`writecheck / notecheck / inboxcheck / workflowcheck / layoutcheck` 都是自建脚本，
各自启动一次 Electron，无断言库、无 CI 接入。
**建议**：迁到 vitest（数据层可直接跑，不必起 Electron）+ 保留少量端到端脚本。
**代价**：中等。**收益**：回归更快、可进 CI。**建议优先级**：中。

---

## O8 · 主题包只支持强调色 ✅ 已完成

**现状**：目前只支持强调色 + 明暗。
**建议**：把主题包定义为 token 覆盖集（数据驱动），而非代码分支。
**风险**：中（涉及全部颜色 token）。**建议优先级**：中（取决于你是否在意主题包）。

---

## O9 · 富文本编辑器选型 ✅ 已完成

**现状**：笔记用 `textarea`。若要补语法高亮 + `[[` 补全，
可选 CodeMirror 6（轻、可扩展）或自绘高亮层。
**建议**：CodeMirror 6 + 自定义 `[[` 补全扩展。
**代价**：1–2 天。**风险**：中（新依赖、样式需与设计系统对齐）。**建议优先级**：中。

---

## O10 · 文案硬编码中文 ✅ 已完成（骨架 + 高频文案）

**现状**：所有界面文案直接写在 JSX 里。
**建议**：若要出英文版再抽 i18n，否则不做。
**建议优先级**：低。

## O11 · 内嵌 Office 预览需要引入解析库 ✅ 已完成

**现状**：目前是「显示引用路径 + 交给系统默认应用打开」。

**建议**：若要内嵌预览，引入 `mammoth`（docx → HTML，约 500KB）与 `xlsx`（SheetJS，约 1MB），
在渲染进程解析并复用现有的 HTML 清洗管线。
**代价**：+1.5MB 打包体积、两个新依赖。**收益**：可在应用内只读预览 Word / Excel。
**风险**：低—中（解析库对复杂文档的还原度不一）。**建议优先级**：中（取决于你是否真的在应用里看 Office 文件）。
