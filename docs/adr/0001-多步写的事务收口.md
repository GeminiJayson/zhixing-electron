# ADR 0001 · 多步写的事务收口

- 状态：已采纳
- 日期：2026-09-21
- 背景来源：`docs/audit/design-review-2026-09-21.md`（6 模块审计），「多步写没有事务边界」模式命中 15 处，是本次审计中出现次数最多的系统性缺陷

## 1. 问题

一次用户操作需要写多行/多表时，代码把一致性边界交给了业务逻辑自己保证。任一中间步骤失败，库就停在半完成状态，而界面往往还提示成功。

审计列出的具体点位：

| 层 | 点位 | 多步内容 |
| --- | --- | --- |
| 数据层 | `notes.ts:122-134` saveNote | 版本快照 INSERT + 正文 UPDATE + 关联删插 + 改名传播 + 索引重建 |
| 数据层 | `workflow.ts:451-479` instantiateWorkflow | 实例 + 根任务 + 各步骤任务 + 绑定 |
| 数据层 | `inbox.ts:116-136` mergeFlashes | 新条 + 标签复制 + 逐条软删 |
| 主进程 | `task-sync.ts:320-327` 整批同步 | 循环 upsert + 收尾写 last_result |
| 页面层 | `TasksPage.tsx:450` | `for (id of ids) await deleteTask(id)` |
| 页面层 | `TasksPage.tsx:588` | `for (id of ids) await moveTaskToList(id, listId)` |
| 页面层 | `NotesPage.tsx:778-786` | 建任务 → 改 notes_md → 挂段落锚 |
| 页面层 | `WorkflowPage.tsx:838` | 自动布局逐节点写坐标 |
| 组件层 | `CapturePanel.tsx:148-151` | createTask → updateTask(notes_md) |
| 组件层 | `TagManager.tsx:104` | `for (id of picked) await deleteTag(id)` |
| 组件层 | `RecycleBin.tsx:160-162` | 循环逐条 IPC 删除 |

## 2. 现状调查：机制早就有了

这一点决定了本 ADR 的性质 —— **不是引入新机制，而是让已有机制被一致地使用**。

- **事务能力已在用**：仓库里已有约 20 处 `conn().transaction(...)`（`export.ts:326`、`graph.ts:737`、`inbox.ts:99`、`maintenance.ts:40`、`lists.ts:55`、`settings.ts:28/49`、`trash.ts:60/72/84/157`、`workflow.ts:201/275/324/980`、`tasks.ts:561`）。
- **批量范式已经成型**：`task-ops.ts:104-140` 的 `batchComplete` / `batchMove` / `batchSetDue` 就是标准答案 —— 编译期准备好 statement，事务里循环执行，**一次 IPC 完成一个用户操作**。
- **广播时机已经是对的**：`db/index.ts:222-231` 的 `handle()` 包装器是「先 `await fn(...)`，成功后再 `broadcastDataChanged`」。所以只要事务写在 handler 内部，**广播天然发生在提交之后**，不需要额外约定。

**但约定没有被遵守**，最硬的证据：

> `batchMove` 三层齐全 —— 实现（`task-ops.ts:118`）、IPC（`db/index.ts:273` `db:batchMove`）、preload（`preload/index.ts:526`）—— 而 `TasksPage.tsx:588` 仍然自己写 `for (const id of ids) await window.zhixing.db.moveTaskToList(id, listId)`。

结论：**正确做法存在 ≠ 会被采用**。因此本 ADR 的重心是护栏，不是文档。

## 3. 分类

四类问题的收法不同，混为一谈是之前每处各自为政的原因。

**A 类 · 主进程内同步多步写**
同一个 handler 内多次写库，无跨进程边界。→ 直接用 `conn().transaction(...)` 包住。
注意：better-sqlite3 的 transaction 只包裹**同步**执行，函数体内**不能有 await**；含异步步骤的操作必须把异步部分移到事务之外（先提交、再做异步、异步失败不回滚而是补偿或上报）。

**B 类 · 渲染层循环逐条 IPC**
事务无法跨进程，所以逐条 IPC 在原理上就不可能原子。→ 必须**收敛为单个 IPC**：主进程提供批量入口，渲染层一次调用。
已有范例：`batchComplete` / `batchMove` / `batchSetDue`。

**C 类 · 组件层跨 IPC 的复合操作**
如「建任务 → 写备注」。→ 合并成主进程的**单一复合入口**（如 `createTaskWithNotes`），而不是让渲染层串两次 IPC。

**D 类 · 异步批处理**
如外部同步整批 upsert。→ 事务包住整批写，**结果回写**（`last_result`）放在事务内或紧随其后，失败必须让调用方可见（不能 `void runTaskSync()`）。

## 4. 方案

### 4.1 补齐缺失的批量/复合入口

按 B/C 类，在 `task-ops.ts`、`trash.ts`、`workflow.ts` 上补齐，并成对补 IPC + preload：

| 新入口 | 替代 | 说明 |
| --- | --- | --- |
| `batchDeleteTasks(ids)` | `TasksPage.tsx:450` 循环 | 逐个级联软删（复用 `softDelete` 的子树收集），一个事务 |
| `batchDeleteTags(ids)` | `TagManager.tsx:104` 循环 | 复用 `deleteTag` |
| `batchUpdateNodePos(list)` | `WorkflowPage.tsx:838` 循环 | 自动布局一次提交 |
| `batchDeleteTrash(items)` | `RecycleBin.tsx:160-162` 循环 | — |
| `createTaskWithNotes(title, parentId, listId, notes)` | `CapturePanel.tsx:148-151` | 一条复合入口 |
| `attachBlockWithTask`（或让 `createTask` 接受段落锚） | `NotesPage.tsx:778-786` | 三步合一 |

渲染层已有的循环 IPC 一律改为调用这些入口；`TasksPage.tsx:588` 直接用**已经存在的** `batchMove`。

### 4.2 主进程内多步写补事务（A 类）

`saveNote`、`instantiateWorkflow`、`mergeFlashes`、任务同步整批 —— 各自包 `conn().transaction()`，并把 `reindexTask` 这类同步副作用留在事务内、异步副作用移出。

### 4.3 护栏（本 ADR 的核心）

三条，缺一不可：

1. **静态检查**：`src/shared/architecture.test.ts` —— 扫描 `src/renderer/src/**`，断言不存在「循环体内直接 `await window.zhixing.db.*`」的写法。这是把「B 类必须走批量入口」变成可执行断言，而不是一句约定。
2. **行为验证**：给多步写补「中途失败即回滚」的测试 —— 注入一个必然失败的中间步骤，断言库状态与操作前完全一致。优先覆盖 `saveNote` 与 `instantiateWorkflow`。
3. **成对注册检查**：新增写能力时，IPC 与 preload 必须成对；沿用 `WRITE_DOMAINS` 的域声明（该表的漂移问题见审计数据层第 4 条，另行修）。

### 4.4 广播时机（现状正确，写成约定以防回退）

- 事务只写在 handler 内部；**不在事务内调 `broadcastDataChanged`**。
- `handle()` 的成功后广播是唯一定式；不要在 handler 里手工提前广播。
- 批量入口的广播域为所在域的单值（`'task'` / `'workflow'`），不要为省事广播多个域。

## 5. 边界：本 ADR 不做什么

- **不引入 ORM 或迁移到异步驱动**。better-sqlite3 的同步事务已经够用，改动面越小越好。
- **不追求「跨进程事务」**。B/C 类的正解是消灭跨进程的多步，而不是发明分布式事务。
- **不改动 SQLite 的 journal/synchronous 设置**。审计未发现与持久化模式相关的问题。
- **不为已有 20 处 `transaction` 做重写**。它们是对的，不动。

## 6. 落地顺序

1. 补静态检查（先让护栏生效，再改代码 —— 否则改完无法防止回退）
2. 补 A 类四处事务
3. 补 B/C 类六个入口 + 渲染层改调
4. 补 D 类事务与失败回写
5. 补行为验证测试
6. 跑全量回归（单测 + 端到端）
