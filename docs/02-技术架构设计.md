function handle(channel: string, fn: IpcHandler): void {
  ipcMain.handle(channel, async (event, ...args) => {
    const result = await fn(event, ...(args as never[]))
    const domain = WRITE_DOMAINS[channel]
    if (Array.isArray(domain)) for (const d of domain) broadcastDataChanged(d)
    else if (domain) broadcastDataChanged(domain)
    return result
  })

## 4. IPC 与「按域广播」

### 4.1 通道规模

| 来源 | 通道数 | 说明 |
| --- | ---: | --- |
| `src/main/db/index.ts` `registerDbHandlers()` | **185** 个 `db:*` 通道 | 数据层全部能力； |
| `src/main/index.ts` | **56** 个 `ipcMain.handle` | `app:info`、`theme:set`、6 个 `widget:*`、3 个 `window:*` |

### 4.2 写操作广播（O3）

核心设计：**广播写在 IPC 包装器里，而不是散落在每个 handler 中**（`src/main/db/index.ts` 注释）：



- `WRITE_DOMAINS`（`src/main/db/index.ts`）是**唯一**的「写通道 → 域」映射表，本轮实测 **69** 条；读通道不进表。
- 域枚举为 5 个：`'task' | 'note' | 'flash' | 'workflow' | 'settings'`（`src/shared/events.ts`）。
- 支持一次写操作声明多个域：图谱连线编辑动的是两端真数据，`db:connectGraphNodes` / `db:removeGraphEdge` / `db:rewireGraphEdge` 声明为 `['note','task']`。
- 广播实现遍历所有窗口（`BrowserWindow.getAllWindows()`），因此**桌面浮窗也能同步**；同时调用主进程侧钩子刷新托盘。
- 特例：`db:restoreBackup` 成功后**五个域全部广播**，因为整库被替换。
- 已知缺口：`restoreTrash`/`purgeTrash`/`emptyTrash`/`purgeTrashOlderThan`/`import*` 目前统一映射为 `'task'`，note/flash/settings 视图不会自动刷新（详见 `04` 文档 D14）。

### 4.3 渲染侧订阅

`src/renderer/src/App.tsx` 启动时调用一次 `bindHostEvents(window.zhixing.db)`（`src/shared/events.ts`），把主进程的 `data:changed` 接进订阅表；页面用 `subscribeDomain(['note','task'], cb)`（`src/shared/events.ts`）只订阅自己关心的域。

典型订阅点：

| 位置 | 订阅域 | 目的 |
| --- | --- | --- |
| `src/renderer/src/App.tsx` | `settings` | 设置页改主题/字号后主窗重铺外观 |
| `src/renderer/src/pages/GraphPage.tsx` | `note`、`task` | 写作后图谱重查（未含 `flash`） |
| `src/renderer/src/WidgetApp.tsx` | `settings` | 浮窗独立渲染进程自己重铺外观 |

注意：`shared/events.ts` 的主进程侧编译也通过（不引用 `window`），订阅表是**进程内**的，跨进程靠 IPC 广播。

### 5.1 连接与事务约定

- 数据目录支持 `ZHIXING_HOME` 覆盖（`connection.ts`）——这既是便携模式，也让写入验证跑在副本库上。
- PRAGMA：`journal_mode = WAL`、`foreign_keys = ON`、`busy_timeout = 4000`（`connection.ts`）。
- 「零表才算全新库」：用一个 `sqlite_master` 计数判定，避免 0 字节文件让整个应用只会报 `no such table`（`connection.ts`）。
- 建库失败时只清理**自己刚创建**的文件（`creating && !existed`），绝不动用户已有库（`connection.ts`）。
- 时间戳统一写成 `YYYY-MM-DD HH:MM:SS.ffffff`（微秒 6 位），保证各语言/工具解析一致（`connection.ts`）。
- 迁移前强制备份失败即中止（`connection.ts`），宁可打不开也不冒险改主库。
- 索引说明：`SCHEMA_SQL` 含 25 张表 + 3 张 FTS5 虚拟表、**不含任何 `CREATE INDEX`**；唯一的业务索引来自 v12 迁移步骤（`src/main/db/migrate.ts`）。

### 6.1 表清单（24 = 21 业务表 + 3 张 FTS5 虚拟表）



`SCHEMA_VERSION = 18`（`src/main/db/schema.ts`）。该文件是建库 DDL 的唯一真源，随功能直接维护。

### 6.2 schema 的维护方式

库文件不存在时由 `connection.open()` 执行 `SCHEMA_SQL` 建库；每张表都带 `IF NOT EXISTS`，因此同一份 DDL 既能建新库，也能给旧库补上缺失的表。

| 环节 | 事实 | 证据 |
| --- | --- | --- |
| DDL 真源 | `SCHEMA_SQL` + `SCHEMA_VERSION` 都写在 `schema.ts` | `src/main/db/schema.ts` |
| 迁移链 | v1–v12 顺序迁移，旧库自动补齐 | `src/main/db/migrate.ts` |
| 分词 | `cut_for_search` 分词后交 `unicode61` 索引 | `src/main/db/fts-query.ts`、`fts-query.test.ts` |
| 时间戳 | 统一 `YYYY-MM-DD HH:MM:SS.ffffff`（微秒 6 位） | `src/main/db/connection.ts` |

**变更流程（必须遵守）**：改 `SCHEMA_SQL` → 升 `SCHEMA_VERSION` → 在 `migrate.ts` 的迁移链里补上同号步骤 → 旧库下次打开自动补齐。三处只改一半，旧库就会缺表或读不懂新列。

## 12. 已知架构债与维护约定

1. **README 与代码可能不一致**：README 是入口与索引，事实以 `src/**` 为准。
2. **`db/index.ts` 是全仓最长的 IPC 注册点**：新增写通道必须同时更新 `WRITE_DOMAINS`，否则「写操作不广播」这类 bug 不会报错、只会表现为界面不刷新。
3. **模块级单例 `POS_CACHE`**（`GraphPage.tsx`）：跨页面复用的同时，也意味着图谱坐标不随数据清理而失效——节点被删除后缓存条目仍在（内存占用极小，但需知情）。
4. **轮询而非推送**：浮窗 5s、提醒 30s、跨天 60s。三者都是渲染进程计时器，关掉窗口/挂起进程会暂停维护逻辑。
5. **改 schema 必须三处同步**：`schema.ts` 的 `SCHEMA_SQL`、`SCHEMA_VERSION`、`migrate.ts` 的迁移步骤；只改前两处会让旧库缺列。
6. **原生模块 ABI**：`better-sqlite3` 在开发环境与打包产物之间 ABI 不同，`dist` 之后必须跑 `postdist:*` 还原，否则开发模式启动即报错。
7. **文档真源排序**：`src/**` 代码 > `docs/01`–`03` 主文档 > 其余 docs > `README.md`。
